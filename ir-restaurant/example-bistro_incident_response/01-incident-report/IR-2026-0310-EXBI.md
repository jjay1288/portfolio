# Incident report: WordPress compromise

**Case:** IR-2026-0310-EXBI

**Client:** Example Bistro (pseudonym)

**Incident handler:** Ronald Phillips

**Response period:** March 10–18, 2026

**Public edition:** November 15, 2026

## Summary

Visitor redirects led to an investigation of a WordPress site on shared hosting. The response identified a traffic-distribution engine, five distributed webshells, credential-capture hooks, a hidden administrator, and persistence in the filesystem and database. A hosting-panel field also held a ClickFix-style PowerShell downloader.

The response addressed the known persistence mechanisms in a coordinated cleanup, rotated credentials and sessions, and checked the resulting filesystem and site behavior. The initial compromise path remains unresolved. Findings below distinguish retained artifacts from response outcomes documented in the case notes.

## Scope and role

The investigation covered the WordPress archive and database export, live-server samples, database evidence, authentication reconstruction, and hosting-panel findings. Ronald Phillips was the sole responder, responsible for evidence collection, analysis, containment, eradication, credential recovery, and verification. The administrator workstation and external payment system were not independently examined in the retained evidence.

Raw evidence remains private. The public [evidence inventory](../05-evidence/evidence-inventory.md) identifies the artifacts supporting this account without exposing client identifiers or captured credentials.

## Evidence and findings

### Backup comparison

The archive filename dates the backup to March 8. The listing and scan output were generated on March 10; these are different events. The listing contains 18,897 entries and records a 21,890,291-byte database export.

Selected-domain searches returned no matches. Other PHP-pattern searches returned matches and required review. A search result is bounded by its signatures and input coverage; it is not a clean-backup determination.

The listing records `hello-biz-child/functions.php` at 1,095 bytes. The captured live version is 170,140 bytes and contains `__mu_deployer__` markers and restoration logic. The archived listing does not establish the live payload's presence in the backup. The original multi-gigabyte archive was not re-acquired for this public edition, so no new claim of byte-for-byte archive safety is made. The March response chose vendor reinstalls and targeted live-file cleanup instead of relying on an unverified restore point.

### Filesystem and database persistence

Retained samples substantiate the following mechanisms:

- A cache bootstrap reads the `wp_session_tokens_config` database option, providing a restoration path after file removal.
- The live child theme contains a malware-deployment block; captured parent and inactive themes contain administrator-creation backdoor logic.
- Five webshells provide alternate access paths across different WordPress directories.
- The stealth plugin contains hooks for credential-related concealment, mail interception, administrator-activity logging, and WooCommerce harvesting.

The [malware reports](../04-malware-analysis/) describe the observed code and dependencies. The presence of a capability does not establish that every code path executed.

### Captured data

The retained credential file contains nine non-empty records. Six are plaintext; three decode to additional captures of the same two account/password pairs. No third pair was identified in that file. Sensitive values are omitted from this repository.

The database evidence export contains seven JSON records under `_wp_mail_queue_log` (recipient, subject and timestamp, without message bodies) and eleven under `_wp_site_activity`. It records `_wc_analytics_data` as empty. The client's report that WooCommerce was unused for customer transactions is consistent with the empty store; it does not establish the security of an external payment service.

### Initial-access assessment

The hosting-panel downloader and website malware share a domain family. A credential-theft chain involving ClickFix and hosting-panel access is a plausible explanation. The artifact does not prove that a particular administrator executed it, that its second stage harvested browser credentials, or that it was the first entry point. The retained records also consider compromise before the hosting transfer.

The available authentication reconstruction begins after the apparent deployment window. Post-compromise WordPress logins and captured credentials therefore cannot identify who introduced the malware.

## Containment and eradication

Maintenance mode did not prevent direct requests to the webshells when a bypass parameter was supplied. Ronald Phillips applied PHP deny rules in the affected directories and recorded blocked requests across three request variants at 10:05 PDT on March 18 (17:05 UTC).

Cleanup began at approximately 14:37 PDT (21:37 UTC). The evidence-capture script uses server-local `date` without a UTC override. Its snapshot is named `20260318-143745`; the tar member timestamps place the newly created directory and manifest at 21:37:48 UTC. All seven captured files match the accompanying SHA-256 manifest. This establishes the timezone interpretation and snapshot integrity; it is not a substitute for the complete execution log.

The response records describe removal of the known persistence layers, WordPress core and parent-theme reinstalls, removal of the bounded child-theme block, deletion of the hidden administrator, credential rotation, and session invalidation. Follow-up checks led to manual fixes for residual database options and account deletion rather than assuming the script had completed every action successfully.

## Verification and remaining work

The post-eradication record reports matching core checksums, absence of known webshell files and HTTP 404 responses at their former paths, and a Wordfence scan with no issues. These are recorded response outcomes; they were not repeated against the live site for this portfolio.

A rewrite flush unintentionally lifted maintenance mode. The WAF was active when the site returned to service, but this alone does not establish that the transition had no exposure.

The retained record leaves administrator-workstation review, MFA confirmation, selected account reconnections, provider confirmation of the panel cleanup, and notification delivery unresolved. No later completion is inferred. The [recovery checklist](../07-remediation/post-eradication-checklist.md) retains the documented follow-up status.

## Lessons applied

- Treat archive searches as scoped tests and compare suspicious files with known-good sources before choosing a restore point.
- Test containment against the attacker's actual access paths, including bypass parameters and directly callable files.
- Remove restoration dependencies together and investigate failed checks after an automated cleanup.
- Verify timestamps against raw archive metadata before combining local-time and UTC records.
- Separate captured data, malware capability, and demonstrated execution when describing impact.
