### 2. Executive Summary

The WordPress website for Example Bistro (example-bistro.invalid), a restaurant at [REDACTED CLIENT ADDRESS], was compromised as part of a large-scale automated campaign targeting WordPress installations. The threat actor gained initial access through a "ClickFix" social engineering attack -- a fake Cloudflare CAPTCHA that tricked a site administrator into executing an obfuscated PowerShell payload. This payload downloaded and executed a credential-stealing trojan from attacker-controlled infrastructure (`webanalytics-cdn.cfd`), which harvested the SharedHost Provider hosting panel credentials.

Using stolen SharedHost Provider panel credentials, the attacker deployed a full malware kit:

- **1 Traffic Distribution System (TDS) engine** (126KB mu-plugin) that redirects visitors and exfiltrates tracking data
- **5 redundant webshells** distributed across non-standard WordPress directories
- **3 credential-stealing hooks** (wp-login.php injection, theme functions.php injection, mu-plugin authentication filter)
- **1 hidden administrator account** invisible from all WordPress management interfaces
- **1 stealth operations toolkit** that hides the attacker's artifacts, intercepts emails, includes WooCommerce order-harvesting capability, and logs admin activity
- **2 persistence mechanisms** (database-backed auto-restore, advanced-cache.php bootstrap)

Follow-on validation on March 18 identified additional live persistence and theme compromise indicators that were not fully captured in the first server summary:

- **1 malicious standard plugin** (`wp-perf-analytics`) performing XOR-obfuscated JavaScript injection in `wp_footer`
- **TDS self-heal residue** in `.htaccess`, WP-Cron (`_tds_cache_selfheal`), `_tds*` transients/options, and a hidden XOR temp/config file in uploads
- **Theme backdoors** in the active `hello-biz` parent theme and inactive `kaon` and `lemonchili` theme files (`create_admin=erwesdxsas`)
- **A confirmed malicious bounded block** in the active `hello-biz-child/functions.php` file (`/* __mu_deployer__ */`) that restores `session-manager.php`, scatter webshells, and a fallback plugin path. The March 10 `.wpress` archive and the oldest SharedHost Provider backup are not treated as trusted restoration sources for that theme.
- **Direct server-log evidence of operator use** of the `wp_debug_session` backdoor from March 11 through March 16, with matching `session-manager.php(546) : eval()'d code` parse errors preserved from March 10 onward
- **A legitimate SharedHost Provider panel SSO helper plugin** (`sharedhost-panel-login.php`) that creates one-time WordPress admin login URLs by storing `one_time_login_token` values in usermeta and redirecting the panel user through `wp-login.php?user_id=<id>&one_time_login_token=<token>`; the plugin itself is not malware, but any live tokens must be cleared after the panel compromise
- **A partial SharedHost Provider support intervention on March 18** that removed `wp-content/mu-plugins/` and the `TDS_NOCACHE` block from `.htaccess` without removing the remaining file, database, theme, and auth-layer persistence; the infection still requires full coordinated eradication

**Two sets of WordPress credentials have been confirmed stolen in cleartext.** The attacker's infrastructure includes email interception and WooCommerce order data harvesting capability. Customer payment theft was ruled out: the client confirmed WooCommerce was never used for customer transactions, no WooCommerce customer/order records existed, the malware's WooCommerce harvesting store was empty, and card processing occurred outside WordPress.

The evidence supports a credential-theft chain tied to the ClickFix campaign. It does not prove the first compromise point. The oldest SharedHost Provider backup available on March 17 already contained compromised content, so the site was infected by then. Two explanations still fit the evidence: the compromise predated the SharedHost Provider transfer and came with the site, or it happened shortly after transfer through stolen SharedHost Provider credentials. The retained artifacts do not separate those scenarios cleanly.

### 4. Attack Narrative

#### Phase 1: Infrastructure Setup (February 18, 2026)

The threat actor registered four domains in a 40-second window via Global Domain Group LLC:

- `webanalytics-cdn.sbs`
- `webanalytics-cdn.cyou`
- `webanalytics-cdn.cfd`
- `webanalytics-cdn.icu`

All domains were placed behind Cloudflare free-tier CDN for anonymity. Cheap, disposable TLDs (< $1 each) were selected. The identical naming pattern across four TLDs provides redundancy -- if one domain is blocked, the others continue operating.

DNS was activated on February 23, 2026 via Cloudflare.

#### Phase 2: Initial Access (Late February -- Early March 2026)

A site administrator encountered a fake Cloudflare CAPTCHA page (the "ClickFix" or "paste-jacking" technique). The page presented instructions such as:

> "Verify you are human -- Press Win+R, paste this text, and press Enter"

The pasted text was a PowerShell command that:
1. Downloaded a trojan from `https://webanalytics-cdn.cfd/api/index.php`
2. Executed it in a hidden window
3. Self-deleted after execution
4. The trojan harvested saved browser credentials, including SharedHost Provider panel login

**Evidence:** A copy of this PowerShell payload was found planted in the SharedHost Provider SSH/SFTP username field, obfuscated with XOR encryption (key: `pgtPYT`) and disguised with the comment `# I am not a robot - Cloudflare ID: 85f261d8487fffbd`.

#### Phase 3: Malware Deployment (March 8, 2026)

Using stolen SharedHost Provider credentials, the attacker:

1. **Created a hidden admin user** (`adminbackup1d8273`, ID 8) at 18:16:18 UTC
2. **Deployed 5 webshells** across `wp-includes/fonts/`, `wp-content/uploads/`, `wp-content/upgrade/`, `wp-content/languages/`, `wp-content/uploads/woocommerce_uploads/` -- all using auth key `a3f8b2c1d4e5f607`
3. **Deployed 4 mu-plugins**: session-manager.php (TDS engine), wp-user-query.php (stealth toolkit), health-check.php (stub)
4. **Activated a malicious standard plugin**: `wp-perf-analytics` (obfuscated JavaScript injector)
5. **Injected credential stealers / admin backdoors** into `wp-login.php`, `hello-biz/functions.php`, and dormant theme files later confirmed in `kaon/functions.php` and `lemonchili/functions.php`
6. **Replaced advanced-cache.php** with auto-restore mechanism (`_sm_ac_v5`) and added self-heal logic in `.htaccess`, WP-Cron, transients, and uploads temp files
7. **Stored full malware backup** (168KB) in database option `wp_session_tokens_config`
8. **Planted a secondary ClickFix payload** in the SharedHost Provider SSH username field to compromise the next administrator

File modification timestamps from March 8, 15:15-15:16 PDT indicate rapid automated deployment.

#### Phase 4: Active Operations (March 8 -- March 18, 2026)

During the compromise period, the malware:

- **Redirected visitors** to external domains via the TDS engine with tracking parameters
- **Accepted repeated operator traffic** at `/?wp_debug_session=<key>&mode=php`; SharedHost Provider raw HTTPS logs preserve successful and failed backdoor requests from March 11-16 across many source IPs
- **Captured credentials** for 2 confirmed WordPress accounts (webagency: 4 captures, SiteOwnerUser: 2 captures)
- **Intercepted 7 outgoing emails** (WordPress update notifications, user registration, admin email change)
- **Logged 11 admin actions** (logins from 4 IPs, plugin activations, user creation)
- **Disabled auto-updates** to prevent accidental removal of malware
- **Anti-detection active**: scanner-aware code pauses operation when Wordfence, Sucuri, or other security scanners are detected via User-Agent sniffing
- **Maintained self-heal persistence** by reasserting a `TDS_NOCACHE` `.htaccess` block and a recurring `_tds_cache_selfheal` WP-Cron task
- **Preserved alternate re-entry paths** in inactive theme files and a suspiciously modified active child-theme `functions.php`
- **Exercised a dynamic eval path** inside `session-manager.php`; March 10-16 error logs capture repeated parse errors from that code path, proving the backdoor was being actively invoked rather than merely present on disk

### 5. Root Cause Analysis

**Primary Cause:** Social engineering through a ClickFix/paste-jacking attack against a site administrator.

**Confidence / Limits:** The ClickFix-to-stolen-credential chain is the strongest explanation for how SharedHost Provider access was lost. It is not proof of the exact root compromise point. The preserved SharedHost Provider HTTPS logs start on March 10, 2026. The main malware deployment timestamps cluster on March 8, 2026. The oldest SharedHost Provider backup restored on March 17 already contained compromised content. That supports three points:

- The site was definitely compromised by the time the oldest retained SharedHost Provider backup was created.
- A pre-SharedHost Provider-transfer compromise carried into SharedHost Provider fits the evidence.
- A post-transfer SharedHost Provider panel compromise using stolen credentials also fits the evidence.

The current evidence does not support attributing the March 8 deployment to a specific administrator, developer, or workstation.

**Contributing Factors:**
1. No multi-factor authentication on SharedHost Provider panel
2. Credentials saved in browser (stolen by trojan)
3. Four administrator accounts (excessive privilege distribution)
4. No file integrity monitoring in place
5. Shared hosting environment (limited isolation)
6. Hide My WP used a weak, guessable bypass key (`[REDACTED-BYPASS-KEY]`) that reduced the effectiveness of maintenance-mode containment

**Long-term:**
13. **Rebuild the site as a static Next.js application with a headless CMS** — **RECOMMENDED**

    The root causes of this incident — a large PHP attack surface, a complex WordPress plugin stack, a shared database with persistent credentials, and a remotely executable backend — are structural. Hardening the current WordPress installation reduces risk but does not eliminate the underlying exposure. A platform rebuild addresses it at the architectural level.

    **Recommended stack:**
    - **Next.js (Static Site Generation)** — pages are pre-built to static HTML at deploy time; no PHP executes on visitor requests
    - **Sanity CMS** (free tier sufficient) — a hosted headless CMS with a clean browser-based editing dashboard; Site Owner updates menu content the same way she would in WordPress, with no code involvement
    - **Vercel** (free tier sufficient for this traffic volume) — hosts the static output and deploys automatically on every Sanity save; a seasonal menu update publishes in under 60 seconds

    **Security impact:** Eliminates the entire PHP/WordPress/MySQL attack surface that made this incident possible. No login page to brute-force, no plugins to exploit, no database to persist backdoors in, no file system PHP execution. The ClickFix/credential-theft chain that drove this compromise has no equivalent entry point on a static site.

    **Performance impact:** Cold request time drops from 2–8 seconds (PHP + Elementor on shared hosting) to ~50–150ms (static HTML from a CDN edge node). Hosting cost drops to ~$0/month for this traffic profile.

    **Content editing for Site Owner:** Sanity provides a structured editing dashboard — menu sections, dishes, prices, and seasonal descriptions can each be defined as discrete fields rather than free-form page content. Site Owner edits a dish price, clicks Publish, and the live site updates within 60 seconds. No WordPress admin, no plugin conflicts, no login page exposure.

    **Scope estimate:** Approximately 2–4 weeks of developer time to rebuild a 5-page restaurant site. Web Agency or a replacement developer can execute this. The existing Elementor page designs are the reference, not the codebase.

    **Recommended action:** Present this option to ownership as the preferred path forward during the post-incident review. Continue hardening the current WordPress installation in the interim.
